# gpt-oss-20b-uav-doctrine

> LoRA fine-tuning of OpenAI's `gpt-oss-20b` on publicly-released UAV combat doctrine via the Tinker API. Research artifact. **82.6% win rate (95% CI 80.9–84.4%)** over the un-adapted base model.

## What this is

This project fine-tunes a **LoRA adapter** on top of OpenAI's open-weight **`gpt-oss-20b`** (a ~21B-parameter mixture-of-experts model, ~3.6B active) to answer questions about Unmanned Aerial Vehicle / UAS combat doctrine. Training and serving run entirely on the [Tinker](https://thinkingmachines.ai/tinker) managed API — **no local GPU is required at any point**; the laptop only drives the API, builds datasets, and runs evaluation.

The adapter was trained on **18,730 synthetic Q&A pairs** generated by GPT-5.4 from **58 publicly-released, unclassified documents** — US joint/service publications, NATO AJPs, UK JDPs, civil-aviation references (FAA/EASA/ICAO), DoDD 3000.09 and the DoD Dictionary, plus open analyses from RUSI, CNAS, ICRC, CRS, and NPS. The corpus contains no classified, FOUO, CUI, or NOFORN material.

It is evaluated rigorously: a GPT-5.4 pair-wise judge scored v4 against the un-adapted baseline on 1,873 held-out test pairs (factual accuracy, completeness, grounding), and the headline win rate was re-checked with randomized model positions to rule out judge position bias. **The honest story is more interesting than the win rate** — see [Methodology findings](#methodology-findings-worth-highlighting): the single largest behavioral change was teaching a reasoning-tuned base model to *stop* burning its token budget on hidden chain-of-thought and answer directly.

**This is a research artifact.** It is not a decision authority, is not validated for any operational, targeting, or safety-of-flight purpose, and must never substitute for the authoritative doctrinal publications or a qualified human in the loop. Outputs can omit or invent specifics — always verify against the source documents.

## Results at a glance

| Metric | Value |
|--------|-------|
| Base model | `openai/gpt-oss-20b` (~21B MoE, ~3.6B active, 32 experts) |
| Training method | LoRA `r=16`, `α=32`, 2 epochs, `lr=2e-4`, all-linear + lm_head |
| Training corpus | 18,730 synthetic Q&A pairs from 58 public docs (~3.4M corpus tokens; ~3.98M tokens processed over 2 epochs) |
| Total spend | ~$55 single run / ~$62 with full ablation (Azure GPT-5.4 dominates; Tinker LoRA is a placeholder estimate) |
| Win rate vs baseline | **82.6%** (95% CI 80.9–84.4%), n=1,873 |
| Bias-corrected win rate | **80.7%** (95% CI 76.3–85.0%), position-randomized, n=300 |
| Held-out-source win rate | 66.7% (n=15, 95% CI 40–93%) |

All numbers trace to the build journals in [`docs/journal/`](docs/journal/).

## Quickstart — use the model

The published artifact is a PEFT LoRA adapter; load it on top of the base model:

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

BASE = "openai/gpt-oss-20b"
ADAPTER = "meftun/gpt-oss-20b-uav-doctrine"

# System prompt MUST match training verbatim.
SYSTEM_PROMPT = (
    "You are an expert assistant on Unmanned Aerial Vehicle (UAV) combat "
    "doctrine. Provide accurate, concise answers grounded in US, NATO, and "
    "allied doctrinal publications."
)

tok = AutoTokenizer.from_pretrained(BASE)
model = AutoModelForCausalLM.from_pretrained(BASE, torch_dtype="auto", device_map="auto")
model = PeftModel.from_pretrained(model, ADAPTER)
model.eval()

messages = [
    {"role": "system", "content": SYSTEM_PROMPT},
    {"role": "user", "content": "What is the role of UAS in joint targeting?"},
]
inputs = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt").to(model.device)
out = model.generate(inputs, max_new_tokens=300, temperature=0.3, do_sample=True)
print(tok.decode(out[0, inputs.shape[1]:], skip_special_tokens=True))
```

> **Note (MoE LoRA).** The adapter places LoRA on the per-expert projections of the gpt-oss MoE plus attention and `lm_head`. Some `transformers`/`peft` versions represent gpt-oss experts as a fused module and may not apply the per-expert LoRA cleanly under vanilla loading. The model was trained and evaluated through the Tinker sampling API — the **[live demo](https://huggingface.co/spaces/meftun/gpt-oss-20b-uav-doctrine-demo)** is the reference, known-good way to run it. See the [model card](https://huggingface.co/meftun/gpt-oss-20b-uav-doctrine) for details.

## Quickstart — reproduce training

Everything runs through [`uv`](https://github.com/astral-sh/uv) (Python 3.11). Each step consumes the previous step's outputs.

```bash
# 1. Clone (PDFs are in Git LFS — install git-lfs first)
git clone https://github.com/mftnakrsu/gpt-oss-20b-uav-doctrine && cd gpt-oss-20b-uav-doctrine

# 2. Install dependencies
uv sync --extra dev

# 3. Configure credentials (Tinker required; Azure OpenAI for Q&A gen + judge; HF for the tokenizer)
cp .env.example .env   # then fill in TINKER_API_KEY, AZURE_*, HF_TOKEN

# 4. Inventory the corpus (file census + tokenization stats)
uv run python scripts/inventory_data.py

# 5. Clean + chunk the PDFs        → data/interim/chunks.jsonl
uv run python scripts/prepare_corpus.py

# 6. Quality-filter chunks         → drops TOC/bibliography/low-content
uv run python scripts/filter_chunks.py

# 7. Generate Q&A pairs (GPT-5.4)  → ~18.7k grounded pairs
uv run python scripts/full_qa.py

# 8. ChatML render + splits        → data/processed/qa/{train,val,test,held_out_source}.jsonl
uv run python scripts/build_splits.py

# 9. Train the LoRA adapter on Tinker
uv run python scripts/train_phase_a.py

# 10. Evaluate vs baseline with the GPT-5.4 judge
uv run python scripts/eval_phase_a.py
```

The final splits (`data/processed/qa/`) are committed, so you can skip steps 4–8 and go straight to training. See [`scripts/README.md`](scripts/README.md) for every script and [`docs/journal/`](docs/journal/) for what each step actually produced.

## Methodology findings worth highlighting

Four observations from the build that are more useful than the headline number (full detail in [`docs/journal/`](docs/journal/)):

1. **Training-time validation NLL ≠ inference-path eval NLL.** v4's training-time `val_nll` (1.28, via the forward/backward path) sat ~0.71 nats below the same checkpoint's inference-path test NLL (1.99, via `compute_logprobs`). They are on different scales — never pick a checkpoint on training-time val NLL; re-evaluate via the inference path. ([journal 08](docs/journal/08-phase-a-ablation-sweep.md))
2. **Eval NLL did not track judge-perceived quality.** Procedural questions had among the highest NLL but were *not* the lowest-scoring under the judge — *factual* questions were. Loss is not quality. ([journal 09](docs/journal/09-phase-a-eval-report.md))
3. **The biggest SFT win was teaching the model to skip the analysis channel.** The un-adapted base, in `Reasoning: medium`, burns its entire 300-token budget on hidden chain-of-thought and emits no final answer ~92% of the time. v4, trained on direct-answer pairs, learned to answer immediately (mean output 297 → 49 tokens) — most of its measured advantage is this behavioral shift. ([journal 09](docs/journal/09-phase-a-eval-report.md))
4. **Position bias was absent in structured-rubric judging.** Randomized-position re-judging on 300 examples gave a 48.5% position-A preference rate — indistinguishable from chance — reproducing the win rate within 1.9pp. Position bias may be a property of free-form preference judging, not strict rubric judging. ([journal 10](docs/journal/10-position-bias-control.md))

## Honest limitations

- **Specificity drift.** v4 reliably gets the shape of an answer right but can drop or invent specifics (wrong message codes, missing conditions, approximate figures). Treat outputs as a starting point to verify against the cited publication, not a finished answer.
- **The win rate is inflated by baseline budget exhaustion.** Most baseline "losses" are the empty-output behavior above. On the 154 test cases where the baseline *did* produce a final answer, v4 still won **77.9%** — that is the cleaner doctrine-knowledge signal.
- **Held-out-source generalization is anecdotal.** Only 15 unseen-source examples; the wide CI (40–93%) reflects this.
- **No safety / red-teaming pass.** This is a doctrine-QA SFT adapter (milestone M1), not a safety-tuned assistant.
- **English only**, and a **snapshot of doctrine as of May 2026** — newer editions are not reflected.
